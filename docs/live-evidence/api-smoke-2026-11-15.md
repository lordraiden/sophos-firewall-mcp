## Hallazgos que corrigen o completan el contrato

1. **`live-users` sí acepta paginación de petición.** El OpenAPI no declara parámetros, pero el appliance honra `page` (`?page=2` → `pages.current: 2`), `pageSize` (`?pageSize=10` → `pages.size: 10`) y `pageTotal` (`pages.items`/`pages.total`). `pageSize=101` → **400 `invalidPageSizeParam`**. Esto no cambia la decisión conservadora de no inventar parámetros en el MCP, pero **sí invalida la afirmación de que el endpoint no permite paginar**; #30 debe decidir con esta evidencia si expone los parámetros observados.
2. **`maxSize` real de `live-users` = 100**, no 1000 como sugería el `example` del contrato. `live-connections/ipv4` sí devuelve `maxSize: 1000`. La metadata de `pages` varía por endpoint.
3. **`pageTotal=true` añade `pages.total` y `pages.items`** (observado en `users`, `firewall/rules/ipv4` y `live-users`). El contrato no lo describía; ahora está verificado.
4. **`pageSize > 100` → 400 `invalidPageSizeParam` en todos los listados probados**, incluidos los que no declaran máximo (firewall rules). El máximo 100 es global en la práctica.
5. **`page=0` se acepta (200, `current: 0`, items vacío)** aunque el contrato declare `minimum: 1`. Es una laxitud del servidor, no un comportamiento a replicar; el cliente debe validar `page >= 1`.
6. **Los envelopes de error no son uniformes:** 401/400 y 404 de recurso son JSON (`{"error":…,"message":…}`); un path inexistente devuelve **404 HTML**; un método no soportado devuelve **405 en texto plano**; `PUT` sobre un path válido devuelve **403 HTML** del front-end. El cliente debe sanitizar y mapear por operación, no asumir JSON.
7. **`GET /firewall/rules/ipv4/{nombre}` funciona con el nombre real** (espacios y puntos, URL-encoded) y devuelve el objeto completo; `GET` sobre rutas POST-only devuelve 404 JSON (`resourceNotFound`) o 405, según la ruta.
8. **Perfil de la clave (inferencia):** existe un administrador dedicado `admin_mcp` activo con perfil **"Read only Admin"** (47 permisos, todos `readOnly`); el perfil "Administrator" tiene 48 `readWrite`. La API no expone qué administrador creó la clave, pero el diseño observado es coherente con mínimo privilegio. No se probaron escrituras para confirmar la denegación por permisos.

## Lo que estas pruebas no demuestran

- Build exacto de SFOS ni compatibilidad general con otras versiones.
- Comportamiento de PATCH sobre arrays, conflictos 409, idempotencia ni escrituras ambiguas.
- Que la clave sea de solo lectura (no se intentó mutar nada).
- Que el `OpenAPI.yaml` del appliance coincida con el del repositorio: no se localizó un endpoint de descarga en `/api/firewall-config/...`.

## Consecuencia para la planificación

- #24 debe incorporar esta evidencia a `API-COVERAGE.md` y al protocolo `pytest -m live`.
- #30 debe decidir explícitamente si expone `page`/`pageSize`/`pageTotal` en `live-users` pese a no estar en el contrato (recomendación: no exponerlos en v1 y documentar la observación, o exponerlos como extensión marcada).
- El cliente REST debe validar `page >= 1` y `1 <= pageSize <= 100` **antes** de enviar, y mapear 401/400/404/405 con envelopes JSON o no-JSON.
- La rotación de la clave es obligatoria al cerrar las pruebas.
